# Tier 2: Vulnerabilities to Test For

These are specific vulnerability classes to check during the Hunt phase. **Primary evidence**: source code review (file, line, reasoning). **Live testing**: only in a non-production test environment with explicit user approval. Format: Check, Do This, Verify.

| # | Check | Do This | Verify |
|---|-------|---------|--------|
| 1 | **XSS (Cross-Site Scripting)** | Confirm framework auto-escaping is enabled globally. No raw HTML insertion (`innerHTML`, `dangerouslySetInnerHTML`, `v-html`, `{!! !!}`) with user-supplied data. Set a `Content-Security-Policy` header that blocks inline scripts. | Inject `<script>alert(1)</script>`, `<img onerror=alert(1)>`, and `javascript:alert(1)` in every text input, URL parameter, and header the app reflects. None executes. CSP blocks any that bypass escaping. |
| 2 | **Path traversal** | Never construct file paths from user input. If unavoidable: resolve the final absolute path and confirm it stays inside the allowed directory. Reject `..`, `%2e%2e`, null bytes, and symlinks pointing outside the boundary. | Request `GET /files/../../../etc/passwd` and URL-encoded variants. The server returns 400 or 404, never file contents outside the allowed directory. |
| 3 | **SSRF (Server-Side Request Forgery)** | When the server fetches a user-supplied URL: allow-list permitted hosts, block `localhost`, `127.0.0.1`, `169.254.169.254` (cloud metadata), `10.*`, `172.16-31.*`, `192.168.*`, IPv6 loopback, and DNS rebinding. Resolve the hostname and check the IP before connecting. | Submit `http://localhost:3000/admin`, `http://169.254.169.254/latest/meta-data/`, and `http://[::1]/`. All are rejected. Submit a DNS rebinding domain — rejected after IP resolution. |
| 4 | **Session management** | Rotate session ID on login (not just on signup). Set absolute and idle timeouts. Support "log out everywhere." Old session IDs are invalid immediately after logout. | Log in — note session ID. Log out — same session ID returns 401. Log in on two devices — "log out everywhere" invalidates both. After idle timeout, session is expired. |
| 5 | **JWT handling** | Use a strong secret (256+ bits) stored outside the repo. Fix the allowed algorithm in code (never accept from the token). Verify `exp`, `iss`, `aud`. Short lifetimes (15 min access, hours refresh). Have a revocation plan. | Tamper with the JWT payload — rejected. Set `"alg": "none"` — rejected. Use an expired token — rejected. Use a token with wrong `aud` — rejected. |
| 6 | **Exposed environments** | No public staging environment. No debug mode (`DEBUG=true`, stack traces, verbose errors) on production. No `.env`, `.git/config`, `package.json`, source maps, or admin tooling accessible via HTTP. | Review source: check server config for directory listing, debug flags, and static file serving rules. Search for `.env`, `.git/`, `package.json`, `*.map` in public/static directories. Confirm error handlers return generic messages (no stack traces). |
| 7 | **Default credentials** | Remove all demo accounts, default passwords, test users, and default admin credentials from every service, database, dashboard, and config file. | Search the codebase for `password`, `admin`, `test`, `demo`, `default`, `changeme`, `12345`. Check `.env.example` has only placeholder values. Try known defaults on login — none work. |
| 8 | **IDOR / BOLA** | Every read, update, and delete endpoint checks that the authenticated user owns or is authorized to access the specific record by ID. Never rely on "the user wouldn't guess the ID." | Log in as User A, note a resource ID. Log in as User B, request User A's resource ID. The server returns 403 or 404, never User A's data. Test with sequential IDs, UUIDs, and predictable patterns. |
| 9 | **API input validation** | Schema-validate every request body, query parameter, and path parameter on the server (use Zod, Joi, Pydantic, or framework validators). Use parameterized queries for all database access. Return only the fields the client needs — never `SELECT *` to the response. | Send: empty body, oversized body, wrong types, extra fields, SQL in string fields, negative numbers where positive expected. The server rejects invalid input with specific error messages. No stack traces leak. |
| 10 | **Exposed logs and dashboards** | Log files, error dashboards (Sentry), database admin (pgAdmin, phpMyAdmin), queue dashboards (BullMQ), and monitoring URLs are behind authentication and network restrictions. | Request common log and dashboard paths. All require authentication. Logs contain no passwords, tokens, or full PII. |
| 11 | **Exposed source maps** | Do not ship `.map` files in production unless you accept the source being publicly readable. If needed for error tracking, upload them privately to your error service. | Check production assets for `.js.map` and `.css.map` files. If found, assess whether source exposure is acceptable. |
