# Tier 3: Advanced Checks

These checks catch deeper issues. Load this file only during the Full mode Hunt phase after Tier 1 and Tier 2 are complete. **Primary evidence**: source code and config review. Live testing only in non-production environments with user approval.

| # | Check | Do This | Verify |
|---|-------|---------|--------|
| 1 | **Vulnerable dependencies** | Run a dependency audit in CI on every push (`npm audit`, `pip-audit`, `osv-scanner`). Update regularly. Remove unused packages. Pin versions in lockfiles. | Run `npm audit` or equivalent. Zero unresolved High or Critical vulnerabilities. All packages are actively maintained (last release within 12 months). |
| 2 | **Malicious packages** | Before adding any dependency: verify it exists on the official registry, check its age, download count, maintainer count, and license. Confirm AI-suggested package names are real — attackers register hallucinated names. Commit lockfiles. | Review every dependency in `package.json` / `requirements.txt`. Each is a real, well-known package. No typosquatted names. Lockfile is committed and matches. |
| 3 | **Unpermissioned AI access** | Any AI feature or agent reads and acts only with the signed-in user's own permissions. Never use a shared admin API key that bypasses user authorization. The AI cannot access another user's data, even if instructed to. | Log in as User A. Ask the AI to show User B's data. The AI returns only User A's data or refuses. Check the backend: AI API calls are scoped to the authenticated user. |
| 4 | **Audit logging** | Record who changed what and when for sensitive data: user records, permissions, billing, settings. Store audit logs separately from application debug logs. Logs are append-only or write-once. | Edit a user record, change a permission, modify a billing setting. Find the corresponding audit entry with: timestamp, actor, action, old value, new value, resource ID. |
| 5 | **Security monitoring and alerting** | Set up alerts for: error rate spikes, failed-login surges (> 10/min from one IP), new admin account creation, unusual API spend, 5xx spikes. Alerts go to a real channel (email, Slack, PagerDuty). | Trigger each alert condition in staging. Confirm the alert fires within 5 minutes and reaches the configured channel. |
| 6 | **Backups and restore** | Automated database backups run on schedule. Backups are stored in a separate location from the primary database. A full restore has been tested end-to-end at least once. Backup encryption at rest. | Identify the backup schedule, storage location, and retention period. Restore a backup into a scratch environment. Verify data integrity. |
| 7 | **Internal dashboard exposure** | Admin panels, database consoles, queue dashboards, monitoring tools, CI/CD dashboards are behind: authentication + authorization + network restrictions (VPN, IP allowlist, or private network). | Review source: check server config and routing for dashboard paths. Confirm authentication middleware is applied. Check for port exposure in Docker/compose files. If the user confirms a test environment is available, verify that dashboard URLs require authentication. |
| 8 | **Security headers** | Set all of these on every response: `Content-Security-Policy` (restricts script sources), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (restrict camera, microphone, geolocation), frame protection via `X-Frame-Options: DENY` or CSP `frame-ancestors 'none'`. | Run `scripts/check-headers.mjs <url>`. All headers present and correctly configured. Cross-check with securityheaders.com. |
| 9 | **Data encryption** | HTTPS everywhere (no mixed content). Database encryption at rest enabled (check provider settings). Connection strings use SSL/TLS. Field-level encryption for the most sensitive data (passwords hashed with Argon2id or bcrypt, payment card numbers tokenized). | Check: all database connection strings include `sslmode=require` or equivalent. Provider dashboard confirms encryption at rest. No plaintext passwords in the database. |
| 10 | **Tenant isolation** | In multi-tenant applications: every database query is filtered by tenant ID. Enforce at the data layer (Row-Level Security policies in PostgreSQL, or equivalent). Not only in application code — a missing WHERE clause must still be safe. | Log in as Tenant A. Directly query the API with Tenant B's resource IDs. The server returns 403 or 404. Check the database: RLS policies exist and are enabled. |
| 11 | **Mass assignment** | Never bind request bodies directly onto database models. Allow-list the specific fields that may be set for each endpoint. | Send a request with extra fields: `{"role": "admin"}`, `{"price": 0}`, `{"is_verified": true}`, `{"tenant_id": "other"}`. The server ignores all unpermitted fields. |
| 12 | **Command injection** | Never pass user input to `exec()`, `system()`, `child_process.exec()`, or shell commands. Use library APIs or strict argument arrays (`execFile`, `spawn` with no shell). | Search the codebase for `exec(`, `system(`, `child_process`, `subprocess.run(shell=True)`. Any that accept user input are findings. Send shell metacharacters (`;`, `|`, `&&`, `` ` ``, `$()`) in fields that reach the system — none execute. |
| 13 | **Insecure deserialization** | Do not deserialize untrusted data with formats that can execute code (`pickle`, `eval`, `unserialize`, `ObjectInputStream`, `yaml.load`). Use plain JSON with schema validation. | Search the codebase for `pickle.loads`, `eval(`, `yaml.load(` (without `Loader=SafeLoader`), `unserialize(`. Each instance with untrusted input is a finding. |
| 14 | **OAuth misconfiguration** | Use exact-match redirect URIs (no wildcards). Include `state` parameter to prevent CSRF. Use PKCE for public clients (SPAs, mobile). Request minimum scopes. Verify token audience. | Change the redirect URI in the OAuth request — the provider rejects it. Remove the `state` parameter — the server rejects the callback. Use a token with wrong audience — rejected. |
